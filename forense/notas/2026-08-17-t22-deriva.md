## 2. La causa raíz, y cómo se aisló

`T22` construye su WARN así (`tests/check.py`, `t22_firmas`):

```
f"{id} ABIERTA desde {creado} ({N} días): {qué_se_firma[:100]}"
```

y `_baseline_key` —la función que decide si un hallazgo es **nuevo** frente a `tests/baseline.json`—
normalizaba únicamente el número de línea:

```python
def _baseline_key(msg):
    return re.sub(r":\d+ ", ": ", msg, count=1)
```

Ese `re.sub` no toca `(<N> días)`. Verificado directamente sobre las dos cadenas reales:

```
clave congelada (14/ago): 'FP-01 ABIERTA desde 2026-08-14 (0 días): M1 · ¿Se adopta el '
clave de hoy    (17/ago): 'FP-01 ABIERTA desde 2026-08-14 (3 días): M1 · ¿Se adopta el '
¿misma clave? -> False
```

**Cada fila `ABIERTA` cambia de clave sola, cada medianoche.** Y el contador congelado en `tests/baseline.json`
lo confirma desde el otro lado: los días almacenados el 14/ago eran `['0','1','2','3','4','9']`.

**La prueba que cierra el caso no es un argumento, es el propio CI de este repositorio.** El run
`31772585548`, sobre `f3873c2`, cerró **success** el 14/ago/2026. Ese mismo commit, sin un byte de
diferencia, corrido hoy:

```
$ git checkout f3873c2 && python3 tests/check.py --baseline
exit = 1
LÍNEA BASE: ROJO — 19 entradas nuevas …
```

Mismo árbol, distinto día, distinto resultado. El mecanismo que `ADR-85` creó para que ninguna firma se
quedara en el limbo estaba, sin que nadie lo viera, volviendo roja toda rama abierta a las 24 horas de cada
recongelado.

**Por qué recongelar solo no servía, y por eso se preguntó.** `_baseline_compare` lee las claves almacenadas
tal cual, sin re-normalizarlas. Un `--freeze` hoy habría guardado `(3 días)`, `(4 días)`, `(7 días)`… y
mañana la corrida produciría `(4 días)`, `(5 días)`, `(8 días)`: rojo otra vez, en las tres PR. La opción
"solo recongelar" compraba exactamente un día.

## 4. Qué se cambió

**`tests/check.py`, `_baseline_key`.** Una línea de normalización más, con su comentario de por qué:

```python
_T22_EDAD_VARIABLE = re.compile(r"\(\d+ días\)")

def _baseline_key(msg):
    msg = re.sub(r":\d+ ", ": ", msg, count=1)
    return _T22_EDAD_VARIABLE.sub("(N días)", msg)
```

**La corrección es de la CLAVE, no del mensaje, y la distinción es todo el punto.** El WARN sigue
imprimiendo los días reales en cada corrida — es la función que `A.12` le encarga, gritar la antigüedad
hasta que alguien la atienda. Verificado: el detalle de la suite sigue diciendo
`FP-01 ABIERTA desde 2026-08-14 (3 días): …`, y `grep -c "(N días)"` sobre la salida completa da **0**.
Lo único que cambia es qué cuenta como regresión **nueva**.

**Universo de la corrección, declarado (A.4/A.10).** Verificado que `T22` es el único test que emite un
contador de días: `grep -n "días" tests/check.py` → una sola línea de código (`:1259`, la de `t22_firmas`),
el resto son comentarios; y de las entradas congeladas en `tests/baseline.json` que contienen `(<N> días)`,
**19 de 19 son de `T22`**. La normalización no puede aflojar ningún otro test porque ningún otro produce esa
forma.

**`tests/check.py`, `_freeze_note`.** La nota interna de `tests/baseline.json` gana su línea de historia
—autorización, mecanismo, y qué absorbe y qué no— como ya hicieron A8-LAND y PROC-10-bis. `congelar no es
aceptar` sigue rigiendo: se dice qué es lo que se congela.

**`tests/baseline.json`.** `--freeze` → `head` `07a1bc6`, 19 fail · 120 warn congelados (claves únicas tras
deduplicar). Necesario, no cosmético: sin él las 19 claves de `T22` seguían almacenadas con su `(0 días)`
del 14/ago y no habrían coincidido nunca con la clave nueva.

**`canon/gobernanza-v1_15.md`** (`ADR-88` + cabecera) y **`canon/estado-programa-v1_10.md`** (`:27`, `:101`)
— cascada de conteo, receta de T15, `87` → `88`.
