# HERRAMIENTAS PARA RENDIMIENTO Y CONSUMO DE SESIONES · recomendación de dirección · 24/sep/2026
**Aterrizada en el repo a `8358b891`: 271 archivos de tests / 1 349 tests; `.git` 363 MB; vistas de 86 MB (65k filas × 1.2 KB); microdato en 1 973 zips, 861 `.dta`, 593 `.csv`, 292 `.dbf`, 187 `.sav`; 103 módulos ya usan pandas/numpy; `registro --escribe` + marcador tardan > 5 min. Dos gastos distintos: tiempo de máquina y tokens de contexto. Los ataco por separado, con el gate D-14 en cada uno: qué defecto real evita, cuánto cuesta.**

## A · Lo que reduce tokens (el gasto que de verdad importa en sesiones CLI)
El contexto se consume leyendo archivos grandes y salidas largas, no computando. Cinco medidas, todas baratas:
1. **`CLAUDE.md` con reglas de lectura** (hoy no hay ninguna): nunca `cat` de un archivo > 200 líneas; `wc -l` primero; `head -n`, `tail -n`, `sed -n 'a,bp'`; `grep -c` antes de `grep`; `git diff --stat` antes de `git diff`; salidas de tests con `-q` y `| tail`; TSV grandes solo por lector CSV con `itertools.islice`. Una regla de dos líneas ahorra más tokens que cualquier librería.
2. **`rg` (ripgrep)** en lugar de `grep -r`: 10–50× más rápido en repos con 363 MB de `.git` y respeta `.gitignore`; `rg -c`, `rg -l`, `rg --max-columns 160` recortan la salida que entra al contexto. Instalar: `apt install ripgrep`.
3. **`jq` y `yq`** para `ejecucion.json`, `spec.yaml`, `manifiesto.yaml` (15 000+ líneas ya): `yq '.[] | select(.id=="ensanut_2022")' data/manifiesto.yaml` en vez de abrir el archivo. Instalar: `apt install jq`; `pip install yq`.
4. **Un índice consultable de RESULT y corridas** (`tools/consulta.py` o DuckDB, ver B.2): `python3 tools/consulta.py result RESULT-ENCIG-MOR-A-P-SOL1` devuelve una línea (valor, unidad, CALC, hash, cuenta_gen2) — hoy una sesión abre `resultados.json` de 1 346 filas para leer un número. Es la medida con mejor razón tokens/esfuerzo.
5. **Clones parciales para sesiones de nube:** `git clone --filter=blob:none` (trae el historial sin blobs hasta que se tocan) y `git sparse-checkout set canon forense tools tests milpa data/corrida0` cuando el acto no necesita `corpus/` ni `data/curacion-universo/` (50 MB de TSV). Menos disco, menos tiempo de arranque, y `git log -p` deja de traer 86 MB por commit.

## B · Lo que reduce tiempo de máquina
1. **`uv` en lugar de `pip`** (`pip install uv`; `uv pip install -r requirements.txt`): instalaciones 10–100× más rápidas y reproducibles con `uv.lock`; CI y cada sesión que hoy hace `pip install --break-system-packages` ganan minutos.
2. **DuckDB** (`pip install duckdb`): consulta TSV/CSV/Parquet con SQL sin cargarlos enteros; `SELECT count(*) FROM 'data/corrida0/resultados.tsv' WHERE cuenta_gen2='SI'` tarda segundos, no minutos; agregaciones ponderadas sobre microdato (`SUM(factor*x)/SUM(factor) GROUP BY sexo, edad`) con réplicas en una sola pasada. Es el motor natural para `registro`, el marcador, `celdas_validadas` y los pisos; convive con pandas (interoperable con DataFrames) sin reescribir nada de golpe.
3. **Polars** (`pip install polars`) para lo que hoy es pandas puro: lectura de CSV/TSV lazy, multi-hilo, 5–20× más rápido y con una fracción de la memoria; API parecida a pandas. Para los 103 módulos con pandas no se migra todo: se migra el derivador de vistas y el marcador, que son los que tardan.
4. **Parquet como caché de microdato** (`pyarrow`): convertir una vez cada `.dta`/`.sav`/`.dbf`/`.csv` a Parquet columnar en caja (`data/cache/parquet/<id>.parquet`, fuera del manifiesto: es caché, el sello sigue siendo el payload original). Lectura de ENOE trimestral o ENSANUT pasa de decenas de segundos a décimas; DuckDB y Polars lo leen directo. `pyreadstat` ya está para `.dta`/`.sav`; `dbfread` (`pip install dbfread`) para `.dbf`.
5. **Hash rápido con `sha256sum` de coreutils y bloques grandes** para 2.5 TB de adquisición: el `hashlib` de Python en bloques de 1 MB es ~3× más lento que `sha256sum`; el manifiesto sigue en sha256 (no cambiar el algoritmo: los sellos existentes lo usan); `blake3` (`pip install blake3`) solo para cachés internos si hace falta.
6. **`pytest-xdist`** (`pip install pytest-xdist`; `pytest -n auto`) para los 1 349 tests: los actos corren la suite completa al cierre; en paralelo se divide por el número de núcleos. `check.py --parallel` ya existe para T35; extenderlo. `pytest --lf` (solo los que fallaron) en iteración.
7. **Perfilar antes de optimizar:** `py-spy record -o perfil.svg -- python3 tools/corrida0.py registro --escribe` dice en un minuto dónde se van los cinco; `hyperfine` para comparar antes/después. Sin esto, cualquier migración es fe.
8. **`orjson`** para `ejecucion.json`/`resultados.json` (3–10× más rápido que `json`; drop-in con `orjson.loads`). Bajo costo, ganancia modesta; solo si el perfil lo señala.

## C · Lo que NO recomiendo
- Git LFS (decidido: cuota de ancho de banda; las vistas ya caben).
- Reescribir los 103 módulos de pandas a Polars: migrar solo los que el perfil marque.
- Cambiar sha256 por otro hash en el manifiesto: rompería la verificación de 344 sellos.
- Bases de datos servidas o motores de workflow (D-14): DuckDB es un archivo, no un servidor.

## D · Cómo entra al repo (un acto de tubería, nube, autónomo)
`GEN2-TUBERIA-RENDIMIENTO-1`, cuatro piezas: (1) `CLAUDE.md` con las reglas de lectura + `rg`/`jq`/`yq` en `requirements-dev.txt` y en CI; (2) `tools/consulta.py` (o DuckDB) con `result`, `corrida`, `celda` como subcomandos de una línea de salida; (3) perfil de `registro --escribe` y del marcador con `py-spy`, y migración del cuello a DuckDB/Polars con test de equivalencia byte a byte de las vistas; (4) `uv` + `pytest -n auto` en CI y en `/acto`, con tiempo antes/después en la nota. Criterio de «hecho»: tiempo de `registro --escribe` y de la suite medido antes/después; una sesión que sigue `CLAUDE.md` no abre un archivo > 200 líneas sin `head`. Si mesa lo pide, lo escribo como encargo completo; los cinco de caja y los tres de nube en vuelo no lo necesitan para terminar.
